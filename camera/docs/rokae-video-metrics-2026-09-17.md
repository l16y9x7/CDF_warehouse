# ROKAE 视频指标与问题记录（2026-09-17）

## 指标体系与含义

本报告统一使用以下指标。每个指标都标明测量边界，避免把配置值、进程状态和真实播放效果混为一谈。

| 类别 | 指标 | 含义 | 主要用途 |
|---|---|---|---|
| 采集 | 分辨率、像素格式 | ROS 实际发布的图像尺寸和编码 | 判断相机输出是否符合配置 |
| 采集 | 采集帧率 | 相机/驱动产生帧的频率 | 判断采集端是否掉帧 |
| 新鲜度 | ROS timestamp age | 当前时间减 ROS 消息时间戳 | 判断帧是否过期或时钟异常 |
| RGB-D | 原始深度、对齐深度尺寸 | 深度是否仍在深度坐标系，或已映射到彩色坐标系 | 防止 RGB 和深度像素错位 |
| RGB-D | CameraInfo 尺寸与内参 | 该图像对应的标定参数 | 判断是否误用了另一坐标系内参 |
| 推流 | 输入来源 | `pipe:0` rawvideo 或 HTTP MJPEG | 确认是否绕过 HTTP 中间编码 |
| 推流 | 编码输出 | H.264、分辨率、帧率、码率 | 判断平台输出是否符合目标 |
| 推流 | `online` / `source_ready` | 编码器进程和最新 ROS 帧是否存在 | 快速运行状态，不等于云端可播放 |
| 推流 | restart / failure reason | 编码器重启次数和具体原因 | 判断断流、阻塞、网络问题 |
| 网络 | interface throughput | 网卡单位时间收发字节 | 估计实际网络负载 |
| 网络 | TCP Send-Q | 内核尚未发出的发送缓存 | 判断上传端是否持续积压 |
| 网络 | RTT、delivery rate | TCP 往返时间和内核交付速率估计 | 判断链路时延和传输能力 |
| 网络 | retrans/lost、网卡 dropped/errors | TCP 重传/丢包与网卡错误计数 | 判断链路质量；不能直接等同视频丢帧 |
| 云端 | WSS/FLV bytes | 从平台播放地址收到的字节数 | 证明平台确实有数据 |
| 云端 | ffprobe metadata | 平台实际输出 codec/分辨率/名义帧率 | 核对平台流格式 |
| 云端 | decode exit / decoded frames | 实际解码是否成功 | 比进程在线更接近播放验收 |
| 资源 | CPU、RSS | 进程 CPU 和常驻内存 | 判断端侧资源压力 |
| 稳定性 | 连续时长、重启次数 | 指标在一段时间内是否保持 | 区分短时成功和长稳运行 |

配置值是“系统想要的值”，实测值是“采样时观测到的值”；两者不一致时以实测为准，并记录差异原因。

本次将 Media 输入切为直接订阅 ROS 彩色图像，经 rawvideo 管道送入 FFmpeg；HTTP 图像接口保持并行。原生相机驱动仍是唯一硬件 owner。现场编码码率已从每路 `1000k` 调为 `300k`，输出保持 `640×480 @ 8 FPS`；此修改仅用于现场，通用三相机模板不变。

代码版本为 `34b72c6`。本文记录短时检查与配置口径，不代表长时间稳定运行验收。证据来自任务 `.trellis/tasks/09-16-vision-config-contract-consolidation/STATUS.md` 及现场只读采样。

## 1 Mbps 阶段的网络症状

| TCP 指标 | 流 1 | 流 2 | 口径 |
|---|---:|---:|---|
| Send-Q | 658970 字节 | 563191 字节 | TCP 发送侧积压快照，不是视频缓存时长 |
| RTT | 3242.47 ms | 3662.53 ms | TCP 往返时间，不是单向网络延迟或端到端视频延迟 |
| delivery rate | 449312 bps | 406504 bps | TCP 对交付速率的估计，不是按时间窗统计的实际应用吞吐或链路容量 |
| 编码配置 | 1000k | 1000k | 每路目标/最大码率参数 |

两路发送队列均超过 0.5 MB，TCP RTT 达到数秒，估计交付速率约 0.4 Mbps，而每路编码配置为 1 Mbps。该组证据支持当时存在发送积压与传输受限，随后出现管道写超时及编码器恢复；不能把首轮成功解码解释为 1 Mbps 持续无中断。具体瓶颈位于无线、运营商、路由还是服务端，尚未定位。

现场降为每路 300k 的目的，是减少编码输出对当时传输能力的压力。是否改善需对照后续采样，不能只凭配置值判断。

## 已修复问题与剩余问题

- **原始管道启动期限过短。** 首次切换时 ROS 两路均新鲜，但 0.5 秒写入期限触发，编码器被终止。相同命令输出本地 FLV 时首帧写入 0.131 秒、后续 0.004–0.006 秒，指向 RTMP 建连/输出等待而非原始编码能力不足。现采用 10 秒启动窗口的递减宽限，稳定阶段单次写入上限 2 秒；靠近窗口末尾仍至少保留 2 秒，因此不是严格全流程 10 秒截止。停止与源新鲜度每 50 ms 检查，过期时终止整个编码器，避免部分帧破坏 rawvideo 边界。
- **错误原因丢失。** 原先仅显示退出码 `-9`；现按编码器实例保留管道阻塞、ROS 源过期等具体原因。
- **HTTP 订阅恢复仍需跟踪。** 变更前头部原生 ROS 图像新鲜，而 HTTP Owner 报时间戳过期。ROS 直推在头部 HTTP 仍不可用时已能云端解码，证明新路径不依赖 HTTP。随后仅重启 HTTP Owner，恢复头部 1280×720、右手 640×480 JPEG。根因尚未定位，需继续调查订阅重连与 QoS 行为，不能把重启恢复视为彻底修复。
- **没有量化视频端到端延迟、实际丢帧率或性能提升。** 最新帧采样会有意跳过未消费帧，但未记录现场跳帧数量；不宣称零丢帧、具体加速比例或零拷贝。

## 验证范围

本地完整测试 100 项通过（17.090 秒），现场 Conda 完整测试 100 项通过（11.559 秒）。覆盖 HTTP 兼容、ROS 输入隔离、最新帧与时间戳、帧率节拍、部分写入、阻塞/源失效/停止、重连、并发生命周期和错误原因保留。真实本地 FFmpeg 将 16 帧 BGR 编码为 H264 FLV，成功解码 16 帧 640×480 @ 8。

这些测试与云端短时解码证明功能和有界恢复机制，不替代真实网络长时间稳定性测试。下面补充 300k 阶段采样后，再判断该设置下的短时表现。

## 当前问题清单

- 网络上行能力与原 1000k/路配置不匹配，表现为 TCP 发送积压、RTT 数秒和编码器原始管道阻塞。现场已改为 300k/路，仍需长时间稳定性测试。
- HTTP Owner 曾出现头部 ROS 时间戳过期，但同一时间原生 ROS 彩色帧新鲜；重启 HTTP Owner 后恢复。订阅重连/QoS 根因尚未定位。
- 目前没有视频端到端延迟、逐帧丢失率、曝光到云端显示延迟、编码质量 VMAF/PSNR 等指标。
- 当前指标为短时采样，不能替代 30 分钟或更长的连续运行验收。

### 结论

两台设备都已完成“ROS 采集与推流并行”的短时验收。`.135` 的主要瓶颈是网络上行能力：
配置码率高于当时 TCP 实际交付能力，产生 Send-Q 积压和 rawvideo 写阻塞；300k 是当前
现场缓解参数。`.105` 的 RTT 和 Send-Q 快照明显较低，但只代表一次采样，不能据此断言
网络长期稳定或两台设备性能完全相同。

后续应统一进行 30 分钟稳定性测试，记录每路实际帧数、重连次数、每次 Send-Q、RTT、
delivery rate、CPU/RSS、网卡 dropped/errors 以及平台解码帧数，再决定是否恢复更高码率。
