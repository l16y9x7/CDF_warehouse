`WorkflowState` 只在 Agent 内部流转，不作为能力接口的请求体。外部平台通过 Agent 任务接口驱动 Sorting 和 Review，并直接提供各货架的行、列字段；底盘固定点位表由 Agent 在启动时加载并校验。

## **1\.1 外部平台 \-\> Agent 任务接口**

外部平台负责业务编排，Agent 负责单个任务内部的状态机和能力调用。本节共定义 4 个接口：3 个异步任务提交接口和 1 个任务终止接口。

| 方法 | 路径 | 用途 | 请求成功后的同步响应 | 最终结果 |
|---|---|---|---|---|
|`POST`|`/agent/sorting/item`|拣选并放置单件商品|`ACCEPTED`|通过 Agent 配置的 `callback_url` 回调|
|`POST`|`/agent/sorting/finish`|Sorting 收尾：导航并推出目标篮筐|`ACCEPTED`|通过 Agent 配置的 `callback_url` 回调|
|`POST`|`/agent/review`|取筐、盘点并汇总复核结果|`ACCEPTED`|通过 Agent 配置的 `callback_url` 回调|
|`POST`|`/agent/terminate`|请求终止当前任务|`ACCEPTED`|取消结果回调到 Agent 配置的 `callback_url`|

### **1\.1\.1 异步任务的通用约定**

3 个任务提交接口都使用 UTF\-8 JSON 请求体，并都必须携带：

| 字段 | 类型 | 约束 |
|---|---|---|
|`task_id`|string|必填，由外部平台生成，全局唯一|

`callback_url` 不在请求体中传入，由 Agent 配置文件统一配置为最终结果的 HTTP(S) 回调地址。

任务成功受理时立即返回 HTTP 200：

```JSON
{"task_id": "task-001", "status": "ACCEPTED"}
```

`ACCEPTED` 只表示 Agent 已受理任务，不表示任务已执行成功。同一 `task_id` 重复提交时，Agent 返回相同的受理响应，不重新创建或执行任务。

每个 Agent 进程对应一台机器人，同时只运行一个 Workflow。已有活动任务时，提交不同任务返回 HTTP 409：

```JSON
{"error_code": "ROBOT_BUSY"}
```

请求无效、依赖模块未就绪或其他受理失败时，返回非 `2xx`，响应体至少包含 `error_code`；返回非 `2xx` 时不会执行任务。

### **1\.1\.2 单件商品拣选**

`POST /agent/sorting/item`

作用：执行单件商品的导航、抓取、条码校验和入篮，成功后仅表示当前商品完成，不自动选择下一件商品，也不自动进入 Sorting 收尾。

请求体字段：

| 字段 | 类型 | 约束 |
|---|---|---|
|`task_id`|string|必填，由外部平台生成，全局唯一|
|`sku_id`|string|必填，商品编码|
|`name`|string|必填，商品名称|
|`agv_row`|string|必填，`L1` 至 `L5`|
|`agv_column`|string|必填，`1` 或 `2`|
|`basket_row`|string|必填，`L1` 至 `L4`|
|`basket_column`|string|必填，`1` 至 `5`|

同步输出：任务成功受理时返回 HTTP 200：

```JSON
{"task_id": "sorting-item-001", "status": "ACCEPTED"}
```

`ACCEPTED` 只表示任务已受理，不表示商品已完成。最终结果通过回调返回，见 1.1.6；成功时 `info.result.sku_id` 为已放入篮筐的商品编码。

### **1\.1\.3 Sorting 收尾**

`POST /agent/sorting/finish`

作用：在外部平台确认全部商品任务成功后，导航到目标篮筐列并推出篮筐。该任务不遍历商品，也不判断整单数量。

请求体字段：

| 字段 | 类型 | 约束 |
|---|---|---|
|`task_id`|string|必填，由外部平台生成，全局唯一|
|`basket_row`|string|必填，`L1` 至 `L4`|
|`basket_column`|string|必填，`1` 至 `5`|

同步输出：任务成功受理时返回 HTTP 200：

```JSON
{"task_id": "sorting-finish-001", "status": "ACCEPTED"}
```

任务依次执行目标篮筐列导航和推筐。最终结果通过回调返回，见 1.1.6。

### **1\.1\.4 复核任务**

`POST /agent/review`

作用：取下指定篮筐，逐件抓取并识别篮中商品，将商品移至复核桌，在确认篮筐为空后比较实际清单与期望清单。

请求体字段：

| 字段 | 类型 | 约束 |
|---|---|---|
|`task_id`|string|必填，由外部平台生成，全局唯一|
|`order_id`|string|必填，外部平台的订单标识|
|`basket_row`|string|必填，Review 视角的行号，`L1` 至 `L4`|
|`basket_column`|string|必填，Review 视角的列号，`1` 至 `5`|
|`expected_items`|array|必填，订单期望商品清单|
|`expected_items[].sku_id`|string|必填，商品编码|
|`expected_items[].count`|integer|必填，大于 0|

Agent 在任务内部完成取筐、盘点、商品条码识别、放置和汇总。同步输出：任务成功受理时返回 HTTP 200：

```JSON
{"task_id": "review-001", "status": "ACCEPTED"}
```

最终结果通过回调返回，见 1.1.6。成功时 `info.result` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
|`review_status`|string|`PASS` 表示无差异；`DISCREPANCY` 表示存在差异|
|`missing`|array|订单内的 SKU 实际数量不足|
|`extra`|array|订单内的 SKU 实际数量超出|
|`wrong`|array|实际 SKU 不在订单中|

`missing`、`extra` 和 `wrong` 的元素结构统一为 `{"sku_id": "sku-001", "count": 1}`。`PASS` 和 `DISCREPANCY` 都表示复核流程正常完成，回调 `status` 均为 `SUCCEEDED`。

### **1\.1\.5 终止当前任务**

`POST /agent/terminate`

该接口无请求体，不传 `task_id`，作用对象始终是当前 Agent 正在执行的任务。

存在活动任务时返回 HTTP 200：

```JSON
{"task_id": "task-001", "status": "ACCEPTED"}
```

`ACCEPTED` 只表示 Agent 已受理终止请求。任务退出前重复调用本接口，返回相同结果。Agent 采用协作式终止：等待当前同步能力调用返回或超时，再停止执行后续节点；本接口不提供底盘或机械臂硬件急停。任务实际退出后的回调见 1.1.6。

Agent 空闲时返回 HTTP 409：

```JSON
{"error_code": "NO_ACTIVE_TASK"}
```

### **1\.1\.6 统一最终回调**

Agent 向配置文件中的 `callback_url` 发送 `POST`。对外最终状态只有 `SUCCEEDED`、`FAILED`、`CANCELLED`。外部平台以 HTTP 2xx 确认；失败时按有限次数重试，不回退为轮询。

拣选成功：

```JSON
{"task_id": "sorting-item-001", "status": "SUCCEEDED", "info": {"message": "任务完成", "result": {"sku_id": "sku-001"}}}
```

Sorting 收尾成功：

```JSON
{"task_id": "sorting-finish-001", "status": "SUCCEEDED", "info": {"message": "任务完成", "result": {}}}
```

复核通过：

```JSON
{"task_id": "review-001", "status": "SUCCEEDED", "info": {"message": "任务完成", "result": {"review_status": "PASS", "missing": [], "extra": [], "wrong": []}}}
```

复核有差异：

```JSON
{"task_id": "review-001", "status": "SUCCEEDED", "info": {"message": "任务完成", "result": {"review_status": "DISCREPANCY", "missing": [{"sku_id": "sku-001", "count": 1}], "extra": [], "wrong": [{"sku_id": "sku-009", "count": 1}]}}}
```

执行失败：

```JSON
{"task_id": "sorting-item-001", "status": "FAILED", "info": {"message": "任务失败", "error": "EXECUTION_FAILED"}}
```

任务取消：

```JSON
{"task_id": "sorting-item-001", "status": "CANCELLED", "info": {"message": "任务已取消", "error": "任务已取消"}}
```

## **2\. 公共约定**

### **2\.1 传输与响应**

- 请求体和响应体使用 UTF\-8 JSON。

- 未在本规范中定义的字段不属于当前最简接口。

- 请求无效、模块未就绪或执行失败时返回非 `2xx`，响应至少包含：

```JSON
{"error_code": "EXECUTION_FAILED"}
```

### **2\.2 物理动作接口**

以下接口属于物理动作接口：

- `POST /navigation/navigate`

- `POST /pose/prepare`

- `POST /manipulation/pick`       \-\-\-\-\-\-\-\-\-\-\-\-\- 按 SKU 抓取商品或抓取篮筐

- `POST /manipulation/pick_review_item`       \-\-\-\-\-\-\-\-\-\-\-\-\- 复核标准模式任意商品抓取

- `POST /manipulation/place`       \-\-\-\-\-\-\-\-\-\-\-\-\- 放置

- `POST /manipulation/rotate`       \-\-\-\-\-\-\-\-\-\-\-\-\- 旋转商品

- `POST /manipulation/press`       \-\-\-\-\-\-\-\-\-\-\-\-\- 按压按钮（暂不需要，通过平台与WMS对接实现）

- `POST /manipulation/push`       \-\-\-\-\-\-\-\-\-\-\-\-\- 推篮筐

- `POST /vla/pick_review_item`       \-\-\-\-\-\-\-\-\-\-\-\-\- 复核台篮筐内任意商品端到端抓取

- `POST /hand/pick`       \-\-\-\-\-\-\-\-\-\-\-\-\- 灵巧手纸箱端到端抓取

普通物理动作接口成功后统一返回：

```JSON
{"status": "SUCCEEDED"}
```

`/manipulation/pick_review_item` 成功时返回 `SUCCEEDED`，不返回 `NOT_FOUND`。标准 Review Skill 将底层 `SUCCEEDED` 映射为业务结果 `PICKED`，标准流程中的 `NOT_FOUND` 只来自 `/perception/basket/locate_item`。VLA 是物理动作接口中的例外，保留其专用的 `PICKED` / `NOT_FOUND` 业务结果。

物理动作请求必须携带 HTTP Header `Idempotency-Key`。Agent 使用任务上下文中的动作标识作为键；同一物理动作重试复用同一键。缺省或空值时模块返回非 `2xx`。

```HTTP
Idempotency-Key: <action_id>
```

任务和节点状态由 Agent 持久化。物理动作结果未知时，Workflow 立即进入 `WAITING_CONFIRMATION`，不得自动重复该物理动作；具体确认和恢复机制由实现方案另行定义。

### **2\.3 AGV 货架位置（5 行 × 2 列）**

AGV 货架位置固定为 5 行 × 2 列。Sorting 入参直接给出商品所在的行和列：

- `agv_row`：`L1`–`L5`，从下到上，直接作为相关 Pose 的 `level`

- `agv_column`：`1` 或 `2`。面对 AGV 从左到右，`1` 为左列，`2` 为右列。列号不单独对应导航点

接口不接收组合货位 ID。Agent 不拆分或拼接位置字符串，只校验行列取值。AGV 作业点由商品所在列与本次 Sorting 配置工作手共同决定，共三个固定底盘点：`AGV_L`、`AGV_C`、`AGV_R`。目的是让当前工作臂正对目标列：同侧取货停在中间点，跨侧取货把底盘移到目标列外侧。

|`agv_column`|商品位置|`hand`|导航 `nav_id`|
|---|---|---|---|
|`1`|左列|`LEFT`|`AGV_C`|
|`1`|左列|`RIGHT`|`AGV_L`|
|`2`|右列|`LEFT`|`AGV_R`|
|`2`|右列|`RIGHT`|`AGV_C`|

`hand` 取自 `sorting_policy`，同一商品任务内保持不变，不由任务入参传入。行号只决定 Pose `level`，不参与导航点选择。Agent 另将 `agv_column` 映射为左右箱 `side`：`1` → `LEFT`，`2` → `RIGHT`，传给纸箱商品识别和 Sorting 从 AGV 纸箱抓取的位姿估计；篮筐识别、篮筐估姿和复核商品估姿不传 `side`。

|`agv_row`|`agv_column`|`hand`|导航 `nav_id`|Pose `level`|
|---|---|---|---|---|
|`L1`|`1`|`RIGHT`|`AGV_L`|`L1`|
|`L3`|`2`|`RIGHT`|`AGV_C`|`L3`|
|`L2`|`1`|`LEFT`|`AGV_C`|`L2`|
|`L5`|`2`|`LEFT`|`AGV_R`|`L5`|

### **2\.4 篮筐架位置（4 行 × 5 列 × 2 面）**

篮筐架两面相对，每面为 4 行 × 5 列。拣选机器人和复核机器人分别站在相对的两面，外部平台按当前任务视角直接提供 `basket_row` 和 `basket_column`。镜像关系由平台处理，Agent 不换算行列。

- `basket_row`：`L1`–`L4`，从下到上，直接作为篮筐作业 Pose 的 `level`

- `basket_column`：`1`–`5`，面对当前作业面从左到右

接口不接收组合货位 ID。Agent 不拆分或拼接位置字符串，只校验行列取值。拣选任务按列号使用 `SORTING_BASKET_1`–`SORTING_BASKET_5`；复核任务按列号使用 `REVIEW_BASKET_1`–`REVIEW_BASKET_5`。不得跨作业面使用导航点。推筐先进入 `basket_push` Body Pose，再使用当前篮筐实例的 RGB、Depth 和 mask 估计篮筐 6D Pose。

|任务视角|`basket_row`|`basket_column`|导航 `nav_id`|Pose `level`|
|---|---|---|---|---|
|拣选|`L1`|`1`|`SORTING_BASKET_1`|`L1`|
|拣选|`L2`|`4`|`SORTING_BASKET_4`|`L2`|
|复核|`L1`|`1`|`REVIEW_BASKET_1`|`L1`|
|复核|`L4`|`5`|`REVIEW_BASKET_5`|`L4`|

### **3\.3 视觉理解**

相机选择由 Agent/Skill 决定：商品条码识别固定使用头相机 `head`；其他需要视觉定位或估姿的手部操作使用配置工作手的同侧腕部相机，映射为 `LEFT -> left_wrist`、`RIGHT -> right_wrist`。商品条码识别接口接收图片 Base64，其他视觉接口接收相机服务返回的共享图片路径；都不接收 `camera` 或 `hand`。

各接口的输入输出统一为：请求字段表、请求示例、响应示例。标题中的使用场景表示当前 Workflow 是否调用该接口，不表示模块按任务类型切换实现。

## **4\. Agent State**

Sorting 状态按外部任务边界分别持久化：

- `sorting_item_task`：`{task_id, agv_row, agv_column, basket_row, basket_column, item, current_node, sku_barcode, pick_result, place_result, status}`；每个任务只对应一个商品。

- `sorting_finish_task`：`{task_id, basket_row, basket_column, pushed, last_node, status}`。

- `sorting_policy`：`{hand}`，由 Agent 配置加载；同一商品任务和收尾任务内保持不变。抓取后端固定为标准抓取，不作为策略项。

Review 状态按单个外部任务持久化 `task_id`，并继续使用 `review_order_id`、`basket_row`、`basket_column`、`review_policy`、`review_expected_items`、`review_inspected_items`、`review_current_item`、`review_basket_transfer_state`、`review_empty_observations` 和 `review_summary`。

`WorkflowState` 不保存 RGB、Depth、mask 或共享临时路径。每个外部任务都保存 `task_id`、当前节点和小型业务结果。

# **两类业务主流程**

## **1\. Sorting：两类外部触发任务**

Sorting 与 Review 在不同机器人上运行，不共享 Workflow State。Sorting 不接收整单，不在 Agent 内部选择下一件商品。外部平台按业务顺序分别触发两类异步任务：单件商品拣选和 Sorting 收尾，并在请求中直接提供对应货架的行、列。Agent 只完成当前任务，并通过回调推送该 `task_id` 的状态和结果。

任务目标是根据平台提供的篮筐位置，从 AGV 纸箱抓取指定商品并识别、校验商品条码后放入该篮筐；外部平台确认所有商品任务成功后触发收尾任务，Agent 定位目标篮筐并完成推筐。Agent 不自动从商品任务跳转到收尾任务。

单件商品拣选由外部平台针对每件商品分别触发：

1. 校验商品所在的 AGV 货架行列、目标篮筐所在的行列，并检查本次作业依赖的服务是否就绪（Agent 编排模块）。
2. 根据商品所在列（左/右）和本次配置的工作手（左/右）选择 `AGV_L`、`AGV_C` 或 `AGV_R`，再根据行号调整到商品观察姿态（底盘导航模块、位姿控制模块）。
3. 使用标准抓取取出指定商品：位姿估计模块根据商品信息和 RGB\-D 直接识别纸箱内指定商品、估计抓取位姿，再执行抓取（相机模块、位姿估计模块、标准灵巧操作模块）。灵巧手 Capability 暂不接入本流程。
4. 进入抓取后条码准备姿态，执行五位置扫码运动并用左腕相机获取五张原图，逐张识别商品条码，再依据平台/WMS 商品资料与当前任务要求的商品核对（位姿控制模块、标准灵巧操作模块、视觉理解模块、Agent 编排模块）。
5. 根据目标篮筐列号导航到拣选侧对应列，根据篮筐行号进入预放置姿态；现场定位篮筐、估计放置位姿，并将商品放入篮筐（底盘导航模块、位姿控制模块、相机模块、视觉理解模块、位姿估计模块、标准灵巧操作模块）。

所有商品任务成功后，外部平台单独触发 Sorting 收尾任务：

1. 校验目标篮筐的行列（Agent 编排模块）。
2. 按列号导航到拣选侧目标列，按行号进入推筐姿态（底盘导航模块、位姿控制模块）。
3. 重新拍摄并定位篮筐，估计当前篮筐的推动位姿后推筐（相机模块、视觉理解模块、位姿估计模块、标准灵巧操作模块）。

#### **拣选 Skill 编排**

两类 Sorting 任务由以下 Skill 按固定顺序编排。`navigate` 和 `prepare_pose` 是独立的任务记录点；任何后续物理操作明确失败时，Workflow 从该操作所属的起始导航点和摆姿点（若有）重新进入。

编排开始前，由 Workflow 校验并保存当前任务输入，创建对应任务 State，读取 Agent 配置中的 `sorting_policy`，并检查当前流程实际依赖模块的健康状态。这不是独立 Skill。当前固定使用 `STANDARD` 抓取；策略仅配置工作手 `hand`（`LEFT` 或 `RIGHT`，默认 `RIGHT`），同一商品任务和收尾任务内保持不变。Hand 和 VLA 均不进入流程或任务前健康检查。

Sorting 注册以下 Skill；其中 `navigate`、`prepare_pose` 和 `recognize_and_verify_barcode` 与 Review 复用：

|Skill|职责|
|---|---|
|`navigate`|导航到 AGV 作业点或拣选侧篮筐列|
|`prepare_pose`|进入预定义作业姿态|
|`recognize_and_verify_barcode`|Sorting 模式识别并校验商品条码|
|`pick_sku_standard`|由位姿估计模块直接识别纸箱内指定商品、估姿并标准抓取|
|`place_sku_in_basket`|定位目标篮筐、估姿并放入当前商品|
|`push_basket`|定位拣选侧篮筐、估姿并推筐|

1. `navigate`：导航到固定点位

    驱动底盘到固定导航点。AGV 作业不按列号直连点位，而由 Workflow 按 2.3 节用 `agv_column` 与 `sorting_policy.hand` 选定 `AGV_L`、`AGV_C` 或 `AGV_R` 后传入；篮筐作业直接按 `basket_column` 使用 `SORTING_BASKET_1`–`SORTING_BASKET_5`。Skill 只负责导航，不包含视觉检测或后续动作。

2. `prepare_pose`：进入预定义作业位姿

    驱动机器人进入指定 Body Pose。拣选流程的 `AGV_carton_item_inspect` 直接传入 `agv_row` 作为 `level`；`AGV_item_barcode_scan` 是固定条码识别姿态，不传 `level`；`basket_item_place_prepare`、`basket_push` 直接传入 `basket_row` 作为 `level`。Skill 只负责移动，不包含定位、估姿、条码识别或抓放动作。

3. `recognize_and_verify_barcode`（Sorting 模式）：识别并校验商品条码

    机器人在 `AGV_item_barcode_scan` 下调用一次 `/manipulation/rotate(hand)`。该动作完成五个扫码位运动、用 `left_wrist` 拍摄并返回五个 `image_paths`。Agent 按顺序读取原图并编码为 Base64，将当前件 `sku_id`、`name` 和 `image_base64` 逐张传给 `/perception/recognize_sku_barcode`。单张未识别或识别到其他条码时继续处理后续图片，命中当前 `sku_id` 后立即成功；五张均未识别时返回 `SKU_BARCODE_NOT_FOUND`，至少识别到一个其他条码但始终未命中时返回 `SKU_BARCODE_MISMATCH`，两者均进入 `WAITING_CONFIRMATION`。

4. `pick_sku_standard`：从纸箱抓取当前商品

    机器人处于 `AGV_carton_item_inspect` 后，`pick_sku_standard` 使用配置工作手的同侧腕部相机获取 RGB\-D，按 `agv_column` 映射 `side`（`1` → `LEFT`，`2` → `RIGHT`），将 `sku_id`、`name`、`side`、`rgb` 和 `depth` 传给 `/estimation/pick_pose(task_type=SORTING, target_type=sku)`；位姿估计模块直接识别纸箱内指定商品并返回抓取 Pose，再调用 `/manipulation/pick`。`/hand/pick` 仅保留 Capability 契约，当前 Workflow 不调用。

5. `place_sku_in_basket`：将当前商品放入目标篮筐

    机器人已导航到拣选侧目标列并处于 `basket_item_place_prepare` 后，先从 8082 读取当前头部相机外参，再从 8085 获取同次头部 RGB\-D 及内参，调用 25540 `/infer(target_type=basket)`。Skill 将完整篮筐定位响应平铺到 8086 `/manipulation/place`，商品类别使用 `sku_typ`。不再调用 `/perception/locate_basket` 或 `/estimation/place_pose`，也不生成中间 Pose6D。成功只表示当前单件任务完成，不触发收尾。

6. `push_basket`：推出目标篮筐

    机器人处于 `basket_push` 后，先从 8082 读取当前头部相机外参，再从 8085 获取同次头部 RGB\-D 及内参，调用 25540 `/infer(target_type=basket)`。Skill 将完整篮筐定位响应平铺到 8086 `/manipulation/push`。不再调用 `/perception/locate_basket`，也不生成中间 Pose6D。成功后持久化 `pushed=true`。

#### **1\.1 单件商品拣选任务**

`POST /agent/sorting/item`：

请求包含一个商品的 `sku_id`、名称、AGV 货架的 `agv_row`、`agv_column`，以及篮筐架的 `basket_row`、`basket_column`。Workflow 校验行列取值后，按 2.3 节用 `agv_column` 与 `sorting_policy.hand` 选定 AGV 导航点，再依次执行：`navigate(AGV_L/AGV_C/AGV_R)` \-\> `prepare_pose(AGV_carton_item_inspect, level=agv_row)` \-\> `pick_sku_standard` \-\> `prepare_pose(AGV_item_barcode_scan)` \-\> `recognize_and_verify_barcode(sku_id, name)` \-\> `navigate(SORTING_BASKET_{basket_column})` \-\> `prepare_pose(basket_item_place_prepare, level=basket_row)` \-\> `place_sku_in_basket`。成功只表示当前商品已放入篮筐，不触发收尾。

节点明确失败时，可从所属导航和 Pose 记录点重新进入。物理动作结果未知时保持 `WAITING_CONFIRMATION`，不得自动重复该动作。

#### **1\.2 Sorting 收尾任务**

`POST /agent/sorting/finish`：

外部平台确认所有商品任务成功后触发，并在请求中直接提供篮筐架的 `basket_row` 和 `basket_column`。Workflow 节点顺序固定为：

1. 校验 `basket_row` 和 `basket_column`；

2. `navigate(SORTING_BASKET_{basket_column})`，导航到拣选侧目标篮筐列；

3. `prepare_pose(basket_push, level=basket_row)`；

4. `push_basket`，使用当前头部 RGB\-D 调用 `/infer(target_type=basket)` 后平铺推筐，持久化 `pushed=true`。

收尾任务不遍历商品、不判断整单数量。恢复依据输入校验、导航和推筐进度：输入尚未校验时从第 1 步开始；未完成导航从第 2 步开始；已导航但未推筐从第 3 步开始；已推筐返回成功。

## **2\. Review：单个外部触发任务**

Review 与 Sorting 在不同机器人上运行，不共享 Workflow State。Review 任务一次性输入 `order_id`、Review 机器人视角的 `basket_row`、`basket_column` 和订单期望商品清单 `expected_items`。如果上游持有的是 Sorting 视角列号，镜像换算由调度系统在创建 Review 任务前完成。

任务目标是取下指定篮筐并放到复核台，不指定 SKU 地逐件抓取、识别商品条码并移出全部商品；连续两次使用新画面确认篮筐无商品后，将实际盘点清单与订单期望清单统一比较。

复核任务由外部平台触发，按以下顺序完成：

1. 校验从复核侧看到的篮筐行列及期望商品清单，检查本次作业依赖的服务是否就绪（Agent 编排模块）。
2. 导航到复核侧目标篮筐列，按篮筐行号进入预抓取姿态；现场拍摄并估计篮筐抓取位姿，将篮筐抓起（底盘导航模块、位姿控制模块、相机模块、位姿估计模块、标准灵巧操作模块）。
3. 将篮筐运到复核台，进入固定的放筐姿态并释放篮筐（底盘导航模块、位姿控制模块、标准灵巧操作模块）。
4. 反复检查并取出筐内商品：先进入观察姿态，再进入预抓取姿态；拍摄并定位任意一件商品、估计抓取位姿后执行标准抓取（位姿控制模块、相机模块、视觉理解模块、位姿估计模块、标准灵巧操作模块）。VLA Capability 暂不接入本流程。
5. 每抓取成功一件，就进入条码识别姿态，使用头相机直接识别商品条码；Agent 根据平台/WMS 商品资料将条码换算为实际商品编码。识别成功后进入商品放置姿态，把商品放到复核桌并记录实际商品编码，然后继续检查篮筐（位姿控制模块、相机模块、视觉理解模块、标准灵巧操作模块、Agent 编排模块）。
6. 首次未发现商品时，必须重新拍摄篮筐并独立检查；新画面仍未发现商品，才确认篮筐为空。随后比较实际清单与期望清单，汇总缺少、超出和错品结果（相机模块、视觉理解模块、Agent 编排模块）。

#### **复核 Skill 编排**

Review Workflow 不再以节点表描述，而是由以下 Skill 按固定顺序编排。`navigate` 和 `prepare_pose` 是独立的任务记录点；任何后续物理操作明确失败时，Workflow 从该操作所属的起始导航点和摆姿点（若有）重新进入。

编排开始前，由 Workflow 校验并保存 `order_id`、Review 视角的 `basket_row`、`basket_column` 和 `expected_items`，创建 `WorkflowState`，读取 Agent 配置中的 `review_policy`，并检查当前流程实际依赖模块的健康状态。这不是独立 Skill。当前固定使用 `STANDARD` 抓取；策略仅配置工作手 `hand`（`LEFT` 或 `RIGHT`，默认 `RIGHT`），任务运行期间保持不变。VLA 和 Hand 均不进入流程或任务前健康检查。

Review 注册以下 Skill；其中 `navigate`、`prepare_pose` 和 `recognize_and_verify_barcode` 与 Sorting 复用：

|Skill|职责|
|---|---|
|`navigate`|导航到复核侧篮筐列或 `REVIEW_TABLE`|
|`prepare_pose`|进入预定义作业姿态|
|`pick_review_basket`|定位并抓取目标篮筐|
|`place_review_basket`|在固定 Pose 下将篮筐释放到复核台|
|`pick_review_item_standard`|定位任意商品、估姿并调用标准抓取|
|`recognize_and_verify_barcode`|Review 模式识别商品条码并换算实际商品编码|
|`place_review_item`|在固定 Pose 下将商品释放到复核桌|
|`confirm_review_basket_empty`|获取新画面并确认篮筐是否为空|
|`summarize_review_result`|比较实际与期望清单并生成汇总|

1. `navigate`：导航到固定点位

    驱动底盘到固定导航点。复核流程直接按 `basket_column` 使用 `REVIEW_BASKET_1`–`REVIEW_BASKET_5`，并使用 `REVIEW_TABLE`。Skill 只负责导航，不包含视觉检测或后续动作。

2. `prepare_pose`：进入预定义作业位姿

    驱动机器人进入指定 Body Pose。复核流程使用 `basket_pick_prepare`（直接传入 `basket_row` 作为 `level`）、`basket_place`、`basket_item_pick_inspect`、`basket_item_pick_prepare`、`basket_item_barcode_scan` 和 `review_item_place`；每种抓取后端都必须在观察后进入 `basket_item_pick_prepare` 作为抓取开始姿态。Skill 只负责移动，不包含定位、估姿、条码识别或抓放动作。

3. `pick_review_basket`：从篮筐架抓取目标篮筐

    机器人导航到 `REVIEW_BASKET_{basket_column}` 并处于 `basket_pick_prepare` 后，先从 8082 读取当前头部相机外参，再从 8085 获取同次头部 RGB\-D 及内参，调用 25540 `/infer(target_type=basket)`。Skill 将完整篮筐定位响应平铺到 8086 `/manipulation/pick`（`task_type=REVIEW, target_type=basket`）。不再调用 `/perception/locate_basket`，也不生成中间 Pose6D。成功后持久化 `review_basket_transfer_state.picked=true`。

4. `place_review_basket`：将篮筐放到复核台

    机器人持筐导航到 `REVIEW_TABLE` 并处于 `basket_place` 后，调用 `/manipulation/place(task_type=REVIEW, target_type=basket, destination_type=table)`，使用固定放筐位姿且不向动作接口传 Pose。成功后持久化 `review_basket_transfer_state.placed=true`。

5. `pick_review_item_standard`：从篮筐抓取任意商品

    机器人先处于 `basket_item_pick_inspect` 完成观察，再统一进入 `basket_item_pick_prepare` 作为抓取开始姿态。`pick_review_item_standard` 使用配置工作手的同侧腕部相机获取新的 RGB\-D，调用 `/perception/basket/locate_item`、`/estimation/pick_pose(task_type=REVIEW, target_type=sku)` 和 `/manipulation/pick_review_item`；未发现商品时由视觉返回 `NOT_FOUND`，不调用估姿和抓取；底层抓取成功返回 `SUCCEEDED`，Skill 映射为 `PICKED`。返回 `PICKED` 时写入 `review_current_item` 并将 `review_empty_observations` 清零；返回 `NOT_FOUND` 时将这次独立观察记为第一次空筐观察（`review_empty_observations=1`）并转入空筐确认，不得直接结束任务。`/vla/pick_review_item` 仅保留 Capability 契约，当前 Workflow 不调用。

6. `recognize_and_verify_barcode`（Review 模式）：识别条码并记录实际商品编码

    Review 实机扫码动作当前未纳入交付验收。共享 Skill 的预留行为是在 `basket_item_barcode_scan` 下调用一次 `/manipulation/rotate(hand=配置工作手)`，按顺序读取返回的五张左腕原图并逐张调用 `/perception/recognize_sku_barcode`；首个成功识别的条码作为实际 `sku_id` 写入 `review_current_item`，五张均无法识别时进入 `WAITING_CONFIRMATION` 并保持当前持物。

7. `place_review_item`：将已识别商品放到复核桌

    机器人处于 `review_item_place` 后，调用 `/manipulation/place(task_type=REVIEW, target_type=sku, destination_type=table, hand=配置工作手)`，使用固定商品放置位姿且不向动作接口传 Pose 或 `sku_id`。放置成功后才将实际 `sku_id` 追加到 `review_inspected_items`，清空 `review_current_item`，再从 `prepare_pose(basket_item_pick_inspect)` 进入 `prepare_pose(basket_item_pick_prepare)`，开始下一轮抓取。

8. `confirm_review_basket_empty`：使用连续新画面确认空筐

    任一抓取 Skill 返回首次 `NOT_FOUND` 后，重新调用腕部相机获取新的 RGB\-D，并以新 RGB 调用 `/perception/basket/locate_item` 完成第二次独立观察。新画面返回 `NOT_FOUND` 时将 `review_empty_observations` 加至 2 并确认空筐；返回 `FOUND` 时将计数清零并返回商品抓取循环。不确定、接口失败或复用旧画面均不得增加计数或结束任务。

9. `summarize_review_result`：汇总复核差异

    确认空筐后，由 Workflow 在本地将 `review_expected_items` 与 `review_inspected_items` 按 SKU 多重集合统一比较，生成 `missing`、`extra` 和 `wrong`，写入 `review_summary`。无差异时结果为 `PASS`，有差异时为 `DISCREPANCY`；两种结果都表示复核流程正常完成，任务状态为 `SUCCEEDED`。

篮筐转运恢复根据 `review_basket_transfer_state` 路由：未抓筐时从目标篮筐列的 `navigate` 和 `prepare_pose(basket_pick_prepare)` 重新进入；已抓筐但未放筐时从 `navigate(REVIEW_TABLE)` 和 `prepare_pose(basket_place)` 重新进入；已放筐时不得重复抓筐或放筐，直接从 `prepare_pose(basket_item_pick_inspect)` 再进入 `prepare_pose(basket_item_pick_prepare)` 恢复商品循环。当前商品已抓取但尚未完成条码识别或放置时，必须根据 `review_current_item` 恢复当前件，禁止开始抓取下一件。

Review 中根据条码换算得到的实际 SKU 与订单不一致时不暂停：记录实际值、放到复核桌并继续清空篮筐。订单内同一 SKU 实际数量不足记为 `missing`，数量超出记为 `extra`，实际 SKU 不在订单中记为 `wrong`。这些差异属于正常复核结果，不等于 Workflow 失败。

商品条码在旋转一次后仍无法识别时，机器人保持当前持物，Workflow 进入 `WAITING_CONFIRMATION`，不得放置或抓取下一件。人工可以触发当前件重新识别，或提供确认后的实际 SKU 并从商品放置节点恢复；人工终止时任务进入 `FAILED`。只有完成全部商品检查并确认空筐后才能生成最终差异汇总。
